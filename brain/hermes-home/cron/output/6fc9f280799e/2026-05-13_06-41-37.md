## 踩坑记录

### 0. pipeline-context.json 在全链路完成后被清空

**问题**：当 pipeline 全链路完成（Stage D 成功发 TG 后），`raw/pipeline-context.json` 会被清空为 `{}`。但 webhook run-log 的归档 (`logs/pipeline-runs/`) 仍保留完整信息。

**后果**：依赖 pipeline-context.json 获取 stage_c 数据（如 run_id、duration）的 Phase 2 规则（#7-#8）在已完成的 pipeline 上会读到空值，可能误判为"无 stage_c"。

**对策**：判断 completed/idle 时**优先看 webhook run-log 的 frontmatter**：
  1. 最新 run-log 的 `tg_sent: True` → 最可靠的全链路完成信号
  2. 归档 JSON (`logs/pipeline-runs/`) 含 stage_b/c 完整详情，作为回退数据源
  3. pipeline-context.json 只在 pipeline **运行时** 可靠，完成后不可信

**验证方式**：`cat raw/pipeline-context.json` 返回 `{}` 时，通过 `cat logs/pipeline-runs/*.json` 获取归档数据。

### 1. watchdog-state.json 并发竞态

**问题**：cron 每分钟触发，相邻两次 watchdog 实例可能同时运行（前一次写 state 时后一次已读）。两个实例读到 patrol_count=20，都写 21 出去，但后写者覆盖前者，导致一个脉冲丢失。

**症状**：`write_file` 报 "file was modified since you last read it on disk"，但内容看似正常。

**对策**：写 state 前**重新从磁盘读取**，再基于当前值递增 —— 不要信赖内存中的旧值。推荐用 `jq` 原子地原地更新：

```bash
# 原子地递增 patrol_count 并更新 last_patrol_utc
jq --arg t "$(date -u +%Y-%m-%dT%H:%M:%SZ)" \
   '.patrol_count += 1 | .last_patrol_utc = $t' \
   logs/watchdog-state.json > logs/watchdog-state.json.tmp \
   && mv logs/watchdog-state.json.tmp logs/watchdog-state.json
```

这样即使两个实例同时跑，`jq` 的读取→修改→写入操作也不会丢失计数（但两实例可能写同一个值，不过至少不会递减）。

### 2. state 更新后必须 git push

watchdog-state.json 需要同步回远程仓库，否则下一个实例 `git fetch && git reset --hard` 会丢失本地 state 变更。每次修改 state 后执行：

```bash
git add logs/watchdog-state.json
git commit -m "watchdog: cruise #${PATROL_COUNT} - ${STATUS} (${UTC_NOW})"
git push origin main
```
